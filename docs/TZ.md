# QueueLab — черновик ТЗ`

## 1. Цель

QueueLab помогает студентам сдавать лабораторные без многочасового ожидания под дверью,
а преподавателю — принимать работы по честной и прозрачной электронной очереди:
каждый видит свою позицию и прогноз ожидания, порядок не спорится.

## 2. Роли

| Роль | Что может | Сегодня в коде |
|---|---|---|
| **Гость** | Только вход и `GET /health`. | — |
| **Студент** | Вступить в группу по коду, видеть расписание событий, встать в очередь, видеть свою позицию и прогноз, выйти из очереди, смотреть свою историю сдач. | Ручки есть, проверки прав нет |
| **Преподаватель** | Создать группу и событие приёма, вызвать следующего, отметить результат, начислить баллы приоритета, снять санкцию, смотреть аналитику. | Ручки есть, проверки прав нет |
| **Ассистент** | Принимать работы на событии, куда его добавил преподаватель: вызвать студента, отметить результат. Настройки группы не меняет. | — |

Авторизации пока нет: роли зафиксированы здесь, чтобы потом лечь на JWT.
До этого `student_id` передаётся в теле запроса.

## 3. Сущности

**User** — пользователь (в коде пока нет)

| Поле | Тип | Описание |
|---|---|---|
| id | int | |
| full_name | string | ФИО |
| email | string | логин |
| role | `student` \| `teacher` | глобальная роль; ассистент — роль внутри события |
| telegram_id | string, опц. | для уведомлений |

**Group** — группа по предмету (в коде пока нет)

| Поле | Тип | Описание |
|---|---|---|
| id | int | |
| subject | string | «Алгоритмы и структуры данных» |
| owner_id | int | преподаватель |
| join_code | string | код или ссылка для вступления |

**Event** — событие приёма

| Поле | Тип | Описание |
|---|---|---|
| id | int | |
| group_id | int | к какой группе относится |
| title | string | «Сдача ЛР 1–3» |
| room | string | «ауд. 305» |
| starts_at, ends_at | RFC 3339 | время приёма |
| status | `scheduled` \| `open` \| `closed` | назначено / идёт приём / завершено |
| autocheck_required | bool | обязательна ли автопроверка перед записью |

**QueueEntry** — запись в очереди

| Поле | Тип | Описание |
|---|---|---|
| id | int | |
| event_id | int | событие |
| student_id, student_name | int, string | кто записался |
| lab | string | что сдаёт: «ЛР 2» |
| teacher_only | bool | принять должен именно преподаватель |
| priority | int | баллы приоритета |
| status | `waiting` \| `called` \| `done` \| `no_show` \| `left` | ждёт / вызван / принят / не пришёл / вышел сам |
| position | int | место в очереди с 1; `0` — уже не в очереди |
| eta_minutes | int | прогноз ожидания |
| joined_at | RFC 3339 | когда встал в очередь |

Позже: **Submission** (решение и результат автопроверки), **Attempt** (итог сдачи: оценка,
комментарий, что проверить в следующий раз), **Sanction**, **PriorityGrant**.

## 4. Сценарии

1. **Преподаватель создаёт событие приёма** в своей группе: «Сдача ЛР 1–3, 10 ноября, ауд. 305». → `POST /events`
2. **Студент смотрит расписание** событий и открывает нужное. → `GET /events`, `GET /events/{id}`
3. **Студент встаёт в очередь**: указывает лабораторную и при необходимости «только к преподавателю». → `POST /events/{id}/queue`
4. **Студент следит за очередью**: видит свою позицию и прогноз ожидания. → `GET /events/{id}/queue`
5. **Проверяющий ведёт приём**: вызывает студента, отмечает «принят» или «не пришёл». Студент может сам выйти из очереди. → `POST /events/{id}/queue/{entry_id}/status`

Плюс технический сценарий: проверить, что сервис жив. → `GET /health`

## 5. Ручки

Базовый адрес `http://localhost:8080`, тела запросов и ответов — JSON.
Чтение — `GET`, любое изменение — `POST` (включая смену статуса), PUT и DELETE не используем.

| Метод и путь | Кто | Тело запроса | Успех | Ошибки |
|---|---|---|---|---|
| `GET /health` | все | — | 200 `{"status":"ok"}` | — |
| `GET /events` | студент, преподаватель | — | 200 `[Event]` | — |
| `GET /events/{id}` | студент, преподаватель | — | 200 `Event` | 400, 404 |
| `POST /events` | преподаватель | `CreateEvent` | 201 `Event` | 400 |
| `GET /events/{id}/queue` | студент, проверяющий | — | 200 `[QueueEntry]` | 400, 404 |
| `POST /events/{id}/queue` | студент | `JoinQueue` | 201 `QueueEntry` | 400, 404 |
| `POST /events/{id}/queue/{entry_id}/status` | проверяющий; студент — только `left` | `{"status": "..."}` | 200 `QueueEntry` | 400, 404 |

### Тела запросов и валидация

`CreateEvent`

```json
{
  "group_id": 1,
  "title": "Сдача ЛР 4–5",
  "room": "ауд. 305",
  "starts_at": "2026-11-24T10:00:00+03:00",
  "ends_at": "2026-11-24T13:00:00+03:00",
  "autocheck_required": true
}
```

- `group_id` > 0; `title` и `room` не пустые; `title` не длиннее 200 символов;
- `starts_at`, `ends_at` — даты в RFC 3339, `ends_at` позже `starts_at`;
- `autocheck_required` — необязательное, по умолчанию `false`. Новое событие получает статус `scheduled`.

`JoinQueue`

```json
{ "student_id": 21, "lab": "ЛР 3", "teacher_only": false }
```

- `student_id` > 0 (после JWT уйдёт из тела в токен); `lab` не пустая.

Смена статуса

```json
{ "status": "called" }
```

- `status` — одно из `called`, `done`, `no_show`, `left`.

## 6. Ошибки

Один формат для всех ошибок:

```json
{ "error": "not_found", "message": "событие 42 не найдено" }
```

| Ситуация | Статус | `error` |
|---|---|---|
| `id` или `entry_id` — не положительное целое | 400 | `invalid_id` |
| Тело пустое или не JSON, поле не того типа | 400 | `invalid_json` |
| Пустое обязательное поле, неверная дата, неизвестный статус | 400 | `validation_error` |
| Событие или запись не найдены, неизвестный путь | 404 | `not_found` |
| Метод не тот (например, `DELETE /events/1`) | 405 | `method_not_allowed` |
| *Позже:* запись на событие не в статусе `open`, повторная запись | 409 | `conflict` |
| *Позже:* нет токена / нет прав | 401 / 403 | `unauthorized` / `forbidden` |

## 7. Вне скоупа сегодня

- **Хранение.** Postgres и sqlx — на занятии 04. Сегодня `POST` проверяет вход и отвечает «создано», но ничего не сохраняет.
- **Бизнес-правила** (в usecase): 409 на закрытое событие, санкции за неявки, баллы приоритета, распределение по ассистентам, перенос приоритета на следующее событие.
- **JWT**, роли и права.
- **Прогноз ожидания** по истории преподавателя и типу работы — сейчас числа из мока.
- Уведомления (браузер, Telegram), обновление очереди в реальном времени.
- Автопроверка кода в изолированной среде, история сдач, аналитика.
- Группы и вступление по коду, фильтры, пагинация.

## 8. Как проверяем «готово сегодня»

1. `go test ./...` — зелёный.
2. `go run ./cmd/app`, затем `curl localhost:8080/health` → `{"status":"ok"}`.
3. Каждая ручка из таблицы отвечает JSON с указанным статусом, ошибки — в едином формате.
4. `docker build -t queuelab:0.1 .` собирает образ, `docker run -p 8080:8080 queuelab:0.1` поднимает сервис.
5. `scripts/smoke.sh`: ответы `curl` с хоста и изнутри контейнера совпадают.
